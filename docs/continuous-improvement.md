# Continuing improvement

Use the existing Academic GitHub Development routine and its shared active-work
limit. A material incident can take priority. Do not restart paused work or create
a competing schedule merely because another repository now exists.

On a justified cycle, inspect current main, open work, CI and the latest project
receipt. Resume existing work before opening a new branch. Record the current
milestone and any specific reason for deferral.

1. Identify an observed defect, reviewer problem or changed primary source.
2. State the baseline, the desired observation and evidence that would disprove the change's value.
3. Make one bounded change and run the tests that address its concrete risk.
4. Inspect the complete diff and current remote head; preserve concurrent work.
5. Record the result, failures, actual commit/PR, next owner and next evidence gate.

Reuse recent market research until a material change warrants another review.
Code activity, configured schedules and synthetic examples are not independent
adoption, demand, delivery or revenue. Keep unknown costs and the owner's actual
human effort unknown until recorded. Report substantive progress or changed
blockers through the existing task result; no-change runs can remain quiet.

Maintain `docs/improvement-log.json` in the engineering lane. GitHub Adoption alone writes the private project index and nonfinancial launch register; send its owner verified technical handoffs rather than editing those files concurrently.
Repository documentation is the current engineering record; dated Drive snapshots
retain their own revision. Customer, identity, payment and private negotiation
records remain outside Git. Global retains sole financial-workbook ownership.

Public release, external outreach, costs, operative legal terms and new licences
follow the owner's applicable authority and review requirements. Routine development
does not activate those actions. All customer work retains the bank-first gate.
